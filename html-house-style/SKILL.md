# HTML house style

Build every standalone HTML page with this skill. Generated pages tend to share one look (gradient heroes, emoji cards, tiny diagrams), and readers of serious documents find that look untrustworthy. This kit replaces it.

## Order of precedence

1. The reader's explicit request.
2. The host project's existing design system or framework. Inside a codebase that already has its own CSS and components, apply the writing and structure rules here and leave its styling alone unless asked.
3. This guide.

A page generated by code in the repository is changed at its generator, never in the emitted HTML. Inside a host that has its own tests and specs, those replace `check.mjs` and this kit's structure rules; apply only the writing rules, and only where the host has none. A multi-page or multi-view app with routes is out of scope, even when it ships as one generated file.

If the reader asks for a different palette, font or layout, do it and keep the rest of the rules. If they say a page is only for a desktop tool, the phone layout can be rough, but it must not break.

## Fast path

Pick the pattern by what the reader does in the minute after they open the page. For a mixed page, also read PATTERNS.md section 1.

| Pattern | The reader will | Opens with | Density, palette |
|---|---|---|---|
| `decide` | Approve, reject or choose | `.bluf`: answer, ask, why now, cost, stop conditions | doc, paper |
| `understand` | Build a mental model | `.purpose` | doc, paper |
| `look-up` | Find one fact and leave | `.purpose` and a filter | tool, graphite |
| `monitor` | See whether anything needs them | `.bluf` with one status sentence; an "as of" time | tool, graphite |
| `do` | Carry out a procedure | `.purpose` and `.preconditions` | tool, slate |
| `review` | Learn what was found and what to fix first | `.bluf`: verdict, counts by severity, fix first | doc, paper |
| `dataset` | Read the argument, then explore 25 or more records | the main pattern's opening, plus a `section.dataset` | doc, paper |

From the skill folder:

```sh
node tools/page.mjs --rules monitor                 # that pattern's rules, nothing else from PATTERNS.md
node tools/page.mjs --skeleton monitor > body.html   # line 1 meta, line 2 its sections by line number
node tools/page.mjs --snippet callouts               # one component's rule and markup
node tools/page.mjs body.html page.html --check      # the page, then check.mjs: FAIL and WARN only
```

1. **Rules and skeleton.** Read the rules. Set the title in the skeleton's meta line; change the rest only to override the table.
2. **Edit `body.html`** with the Edit tool or a node script, never `sed -i` (BSD and GNU differ). Keep its order and classes; replace the content. Ask for each component by name with `--snippet`: page frame, purpose, utilities, term, footnote, quote, callouts, status and chips, bridge, code, stats, cards and grid, compare, steps, timeline, details, tabs, table, sortable table, dataset, filter bar, entry, finding, preconditions and do-steps, monitor extras, bar chart, figure frame and a diagram, zoned diagram, hand-drawn chart, annotation, form, glossary (`--snippet list` gives each rule). Generate data to a file and put a line `<!-- include: table.html -->` where it goes; assembly replaces it with the file. `node tools/table.mjs rows.json --caption C --source S > table.html` (a sortable table; `--dataset FACET --noun N --chips a,b` for a whole dataset) and `node tools/bars.mjs counts.json --title T --takeaway K --source S > fig.html` (`--width 320 --small` fits a phone); `--help` lists every option.
3. **Assemble with `--check`.** Fix every FAIL, fix each WARN or name it in the handover, and run it again.
4. **Hand over** at the tier you reached (step 9 below). With no browser: "Not rendered. Checked by reading and by check.mjs (0 FAIL, [n] WARN: [why each stands]): [what you read for]. Please look at: [the two or three things only a render can confirm, such as the figure on a phone, dark mode, print]." With no shell, leave out check.mjs.

**Use your brand.** If the reader's company has a brand guide, put its colours and fonts in a `brand.json` once (BRAND.md; copy `brand.example.json`) and add `--brand brand.json` to step 3: `node tools/page.mjs body.html page.html --brand brand.json --check`. Any brand colour the kit had to change for contrast prints first; name those in the handover.

Read only when needed: STYLE-GUIDE 3 (structure), 4 (writing), 7 (figures drawn by hand), 9 (phones, print), 13 (tools); CHECKLIST "Verified by reading" with no shell, "Verified by looking" with a browser.

## Files in this skill

- `PATTERNS.md`: the six page patterns (Decide, Understand, Look up, Monitor, Do, Review). Each one sets the opening, the order of sections, the navigation, what is stored and how the page prints. Read the pattern you choose every time (`tools/page.mjs --rules`), and section 1 for a mixed page.
- `examples/`: one short working page per pattern, plus a contents page. `tools/page.mjs --skeleton` prints the body of the one for your pattern.
- `SNIPPETS.md`: the shortest correct markup for every component, each with its rule.
- `STYLE-GUIDE.md`: the full guide, with the reason behind each rule. The fast path and the skeletons carry its rules for the common case. Open it when you build something a skeleton does not cover: a hand-drawn diagram or chart (section 7), a dense tool (section 13), or a structure none of the examples has (sections 3 and 11).
- `base.css`: the stylesheet. Inline the whole file into a `<style>` tag in every page.
- `template.html`: a decision brief (the Decide pattern), followed by a component gallery that shows every component in `base.css` once. Its head and closing scripts are the ones every page copies.
- `CHECKLIST.md`: run it before you hand anything over.
- `tools/`: `page.mjs` (a pattern's rules, one snippet, a skeleton to edit, and the complete page from it), `bars.mjs` (a bar chart figure from data), `table.mjs` (a table, or a whole `section.dataset`, from records), `brand.mjs` (a brand file as a checked palette) and `selftest.mjs`. Each runs as a module or a command; `--help` lists the options.
- `BRAND.md` and `brand.example.json`: the brand file's schema, what is derived and what is guaranteed, and a complete example.
- `check.mjs`: a static checker with no dependencies. `node check.mjs page.html` (or `bun`, or `deno run --allow-read`). It needs no browser.

## How to build a page

1. **Name the reader's job** (PATTERNS.md section 1). Ask what the reader will do in the minute after they open the page, and pick Decide, Understand, Look up, Monitor, Do or Review. For a mixed request, build the skeleton of the job the reader does first and borrow at most one section from one other pattern. Declare it: `<body class="doc" data-pattern="decide">`. Never invent a seventh pattern.
2. **Set the density and palette from the pattern** (the fast path table). In general, use `body class="tool"` when the reader mainly scans, filters or operates the page and reads fewer than about 300 words of prose; otherwise `body class="doc"`. Palette: `paper` for anything read at length, `slate` for the most conservative audience, `graphite` for dense tools.
3. **Write the opening the pattern names, first.** Decide and Review pages open with `.bluf`: one answer sentence, then a short list (for Decide: the ask, why now, the cost, the stop conditions; for Review: the counts by severity and what to fix first). Understand, Look up and Do pages open with one `.purpose` sentence saying what the page is for; a Do page adds its preconditions. A Monitor page puts one computed status sentence in `.bluf`, with no list, and an "as of" time before the first `h2`. Then write every argument `h2` as a claim a reader could disagree with. Navigation sections (Glossary, Sources, Method, Appendix, Detail) keep plain labels, go last, and carry `class="annex"`.
4. **Start from your pattern's example** with `tools/page.mjs`. By hand: copy the example (or `template.html` without its component gallery), put the full `base.css` in a `<style>` tag in place of the `<link>`, and keep the masthead, the opening, the head script and the closing script, which holds the filter, step progress and print blocks. Keep the contents rail when the page has four or more `h2`s or about 1,200 words or more (Look up, Monitor and Do pages navigate by their index, filters or progress line instead), and write its list into the HTML yourself, with the `.bluf` before `nav.toc`. Delete the palette toolbar unless the page is a tool the reader will live in.
5. **Fill the body** in the order the pattern's skeleton gives, with the components in `SNIPPETS.md`. Use tokens for every colour. Wrap every table in `.table-wrap` and put its source in a `.table-note` after the wrapper. Put every figure in `figure`, with the Enlarge button first, then `.figure-frame`, then a caption whose first sentence is a `<strong>` takeaway.
6. **Generate data, never place it by hand.** Charts and tables from real data come from `tools/bars.mjs` and `tools/table.mjs`; more than about 25 records become a `section.dataset` (a chart that filters a sortable table). A piece you splice in outside `page.mjs --check` gets `node check.mjs --fragment piece.html` first. With no shell, read the module and follow the same arithmetic by hand, and write it in the handover.
7. **Draw diagrams and charts as inline SVG** with the `.d-*` and `.c-*` classes so they follow light and dark. Give every figure SVG `style="--fig-min: Wpx"`, where W is its viewBox width; it then never draws below 1:1, so the 13 and 12 unit label classes show at 13px and 12px. Compute chart coordinates from the data and write the scale in a comment. Use `--cat-1` to `--cat-6` through `.d-cat-N`, `.c-cat-N` and `.key.cat-N` for categories, never a colour in an SVG attribute. Keep any Mermaid source in `<script type="text/plain" class="diagram-source">`, never in an HTML comment (its `-->` arrows end the comment early). Never load a library.
8. **Write plainly.** Define each specialist term on first use with `.term` and `data-def`, and list every term in the glossary. Spell out acronyms on first use. Every measured or external figure names its source and date; your own estimates say they are estimates. No internal codes as names. No em dashes.
9. **Verify, at the highest tier you have.** When the page replaces or restyles an existing one, run `node check.mjs new.html --was old.html` (or, with no shell, list the old page's interactions by reading it) and name in the handover every interaction kept and every one dropped.
   - **Tier 1, a browser is available:** run `check.mjs` if you have a shell, then everything in CHECKLIST "Verified by looking".
   - **Tier 2, no browser:** run `check.mjs` if you have a shell. With no shell, do the same checks by reading the file (CHECKLIST "Verified by reading"), and write the label-size arithmetic for each figure into your handover. Fix what fails. Hand over with the line in the fast path, step 4.
   - Never write "I looked at it" or "it renders correctly" at Tier 2.

## Non-negotiables

- One self-contained `.html` file. No CDNs, frameworks, web fonts, charting libraries or network requests. Vanilla JavaScript only, and the page reads correctly with it off.
- One reader's job per page, declared with `data-pattern`, and the pattern's opening and skeleton.
- Answer first; claim headings for the argument; sequential plans as numbered steps.
- A view someone might share lives in the URL hash; personal progress lives in `localStorage` for that page; nothing else is stored.
- Serif for reading text, system sans for interface, monospace for data. Restrained colour: one accent, a second used rarely, status always a shape plus a word.
- Space and hairlines before boxes. Cards only for real groups, never touching.
- Every figure label is at least 12px at its displayed size, and every figure can be enlarged.
- The page never scrolls sideways on a phone.
- You say what you checked and how. You never claim to have looked at a page you did not render.
