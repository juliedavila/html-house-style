Runbook · Northwind orders service

Rotate the orders database password without downtime

The service always has a working login, because it moves to a second database role before the first one is locked.

Version 4Reviewed 22 Oct 2026About 30 minutes

Follow these ten steps in order to give the orders service a new database password with no failed requests. Tick each step as you finish it; your ticks stay on this page until you reset them.

Before you start

You need
Who
The on-call engineer for the orders service, with a second engineer reachable.
Access
The database admin role on orders-db, write access to the orders/db secret, and deploy rights in the shop namespace.
Time
About 30 minutes. Not between 11:00 and 14:00 UTC, the daily order peak.
Have open
The orders error dashboard and a second terminal for watching logs.

The service logs in as one of two roles, orders_app_a or orders_app_b. Each rotation sets a new password on the idle role, moves the service to it, then locks the role it left.

Rotate the password

Step 1 of 10Go to it
  1. secrets get orders/db --field user

    You should see: orders_app_a

    If you see orders_app_bThe last rotation went the other way. Read a for b and b for a in every step below.
  2. openssl rand -base64 32

    You should see: one line of 44 characters. Keep it in the terminal; do not paste it into chat or a ticket.

  3. psql -h orders-db -U admin -c "ALTER ROLE orders_app_b WITH LOGIN PASSWORD '<new password>';"

    You should see: ALTER ROLE

  4. psql "host=orders-db user=orders_app_b dbname=orders" -c "select 1;"

    You should see: one row with the value 1. A password error means step 3 did not take; repeat it.

  5. secrets put orders/db user=orders_app_b password='<new password>'

    You should see: orders/db: version 8 written (the number is one higher than before). Note the old version number for the rollback.

  6. kubectl rollout restart deployment/orders -n shop
kubectl rollout status deployment/orders -n shop

    You should see: deployment "orders" successfully rolled out within about five minutes, and no rise on the error dashboard.

  7. psql -h orders-db -U admin -c "select usename, count(*) from pg_stat_activity where usename like 'orders_app_%' group by usename;"

    You should see: rows for orders_app_b only. Connections from orders_app_a can take two minutes to close.

    If orders_app_a still has connections after five minutesSomething other than the service uses the old role, often a scheduled job. Stop here. Do not lock the old role until you have found the client and moved it.
  8. psql -h orders-db -U admin -c "ALTER ROLE orders_app_a WITH NOLOGIN;"

    You should see: ALTER ROLE. The role stays in place for the next rotation.

  9. kubectl logs -n shop -l app=orders --since=10m | grep -c "password authentication failed"

    You should see: 0, and a flat error dashboard.

  10. Add a line to the rotation log with the date, your name, the role now in use and the new secret version.

    You should see: the new line at the top of the log.

Done whenThe service connects only as orders_app_b, orders_app_a cannot log in, there have been no login errors for ten minutes, and the rotation log has today's line.

Roll back

Use the part that matches the last step you finished. Each part leaves the service on a login that works.

  1. Errors after step 6: put the old login backRestore the previous secret version, then restart as in step 6.
    secrets rollback orders/db --to <old version>
kubectl rollout restart deployment/orders -n shop
  2. Errors after step 8: let the old role log in againThen roll back the secret as above if the errors continue.
    psql -h orders-db -U admin -c "ALTER ROLE orders_app_a WITH LOGIN;"
  3. Tell the channelPost what failed, which step, and that the service is back on orders_app_a. Open a ticket before trying again.
