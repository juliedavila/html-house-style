How a name lookup finds a server

Every time you open a website, the Domain Name System (DNS) turns its name into an address. This page builds the model one piece at a time, with one worked example all the way through.

A lookup asks up to three servers in turn

Four parties take part. Your laptop asks one question and gets one answer. A recursive resolver does the work in between: it asks a root server, then a top-level domain server such as the one for .com, then the server that holds the answer. The figure numbers the eight messages in order.

You now know the four parties in a lookup. Next: why your laptop talks to only one of them.

The resolver does the asking for your laptop

Your laptop knows the address of one resolver, set by the network you joined: at home, usually your internet provider's; at work, one run by the office. It sends that resolver a single question, "what is the address of shop.example.com?", and waits for a final answer. It never talks to the other three servers.

This split keeps the hard work in one place. The resolver serves many people, so it learns answers once and reuses them for everyone, which matters in the section on caching.

Worked example, part 1. You type shop.example.com. Your laptop's network settings list a resolver at 192.0.2.53. Message 1 goes there. Nothing else leaves your laptop until message 8 comes back.

You now know who asks. Next: how the resolver knows whom to ask.

Each server knows only the next server to ask

No single server knows every address. Each one knows a slice of the name and hands back a referral: the servers that know the next slice. Names are read from the right. The root knows who runs .com; the .com servers know who runs example.com; the authoritative server for example.com knows the address of shop.

Worked example, part 2. The resolver has an empty cache, so it takes every step.

You now know how a cold lookup walks the name from right to left. Next: why most lookups skip almost all of it.

Caching turns most lookups into one question

Every answer carries a time to live: how long the resolver may keep it. Referrals carry one too, and theirs are usually long, so a busy resolver nearly always knows the .com servers already. The more it has cached, the fewer servers it asks.

Worked example, part 3. Four minutes later a colleague on the same network opens the same shop. The resolver kept the answer from message 7 for 300 seconds, so it is still valid: message 1 goes in, message 8 comes straight back, and no other server hears about it. Two minutes after that the answer has expired, and the resolver asks only the authoritative server, because it still holds the referrals.

You now know the whole model: one question from the laptop, referrals from right to left, and caching that shortcuts both. Next: the mistakes people make with it.

Three misreadings cause most of the confusion

  • "The root servers know every address." They know only who runs each top-level domain. They answer every lookup with a referral.
  • "A changed address works everywhere at once." Each resolver keeps the old answer until its time to live runs out. Lower the time to live a day before a planned move, so old answers expire quickly.
  • "My laptop talks to the authoritative server." It talks only to its resolver. If two people on different networks see different answers, they are asking different resolvers with different caches.

Check that you can explain a lookup

Answer each one aloud before opening it.

What does the root server send back, and why?

It does not have it. It knows only which servers run each top-level domain, so it returns a referral to the .com servers.

A site moved to a new address an hour ago. Why can one colleague reach it and another not?

Their resolvers cached the old answer at different times. The one whose cached answer has expired asked again and got the new address; the other is still inside the old answer's time to live.

How many servers does a busy office resolver usually ask for a popular site?

One or none. It almost always holds the referrals, and often the answer itself.

Glossary

Authoritative server
The server that holds the records for a domain and gives final answers about it.
Recursive resolver
The server that takes your laptop's question and does all the asking needed to answer it.
Referral
A reply that does not answer the question but says which server to ask next.
Time to live
How many seconds a resolver may keep an answer before it must ask again.
